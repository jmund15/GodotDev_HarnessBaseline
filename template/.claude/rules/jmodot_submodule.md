# Jmodot Submodule Rules

Jmodot is a git submodule. These rules are **authoritative** for every command that commits, pushes or lands Jmodot work — the commit and push commands, the PR commands, and any batch PR driver.

**Jmodot's primary branch is `master`.** It contains the full codebase. All feature branches are temporary and must be based on `master`.

1. **Branch strategy (two cases):**
   - **{{PROJECT_NAME}} feature worktree** (`claude/<name>`): create a paired `jmodot/<name>` branch from `origin/master`. When the work lands, push it to `master` (rule 9 order); it gets a paired PR only when the {{PROJECT_NAME}} work is a PR.
   - **{{PROJECT_NAME}} main branch** (no worktree): commit Jmodot changes directly to `master`. No intermediate branch needed.
2. **Verify the base before committing:** run `git -C Jmodot branch -r --contains HEAD`. The base is sound when `origin/master` is in the output, or when `git -C Jmodot rev-list --left-right --count origin/master...HEAD` prints `0 N` (ahead-only — the expected no-push state while ON `master`, where `--contains` output is also empty). A non-zero LEFT count (behind or diverged) is a partial branch: STOP and rebase onto `origin/master` first. The branch name does not decide: a paired `jmodot/<name>` branch printing `0 N` is sound. A branch that exists locally is NOT guaranteed to have the full codebase.
3. **Detached HEAD in worktrees:** `git submodule update` puts Jmodot in detached HEAD state. You MUST create/checkout a branch before committing — otherwise commits are local-only and invisible to GitHub.
4. **Branch checkout (handles first AND subsequent pushes):** done when Jmodot's HEAD is on the paired branch, based on `origin/master`, with the remote branch set as upstream when one exists. Check local, then remote; create, track or switch as needed. Never bare `git checkout -b` (fails if the branch exists).
5. **Jmodot PR creation (PR route only):** Handled by `/create_pr`. When the {{PROJECT_NAME}} work is a PR, its Jmodot branch with changes gets a paired PR on the Jmodot remote, created alongside the {{PROJECT_NAME}} PR with bidirectional cross-references.
6. **Merge order (PR route only):** Jmodot branches merge to master FIRST, then {{PROJECT_NAME}} PRs that reference them. The {{PROJECT_NAME}} PR will show an unresolvable submodule reference if Jmodot isn't merged. **After merging Jmodot, do NOT update the {{PROJECT_NAME}} branch's submodule pointer** — leave it pointing at its original commit. GitHub resolves submodule pointers at {{PROJECT_NAME}} merge time. Updating to Jmodot's latest master pulls in unrelated PRs' API changes and breaks the build.
7. **Submodule update after a parent transition:** Before `git checkout`, `git pull` or rebase, record the parent's Jmodot gitlink (`git ls-tree HEAD Jmodot`) and Jmodot HEAD (`git -C Jmodot rev-parse HEAD`). Run `git submodule update --init --recursive` afterward only when Jmodot HEAD equals the old gitlink. Otherwise preserve its checkout and report the divergence; the parent's new pointer does not authorize overwriting independent Jmodot work. The one automatic exception is SessionStart (`session_context_loader.setup_submodule`): it moves a clean checkout that is a strict ancestor of the recorded pin onto the pin, fast-forwarding a branch and detaching a detached HEAD, because that checkout holds no independent work. A dirty, ahead or diverged checkout stays.
8. **Branch cleanup:** the agent deletes no branch on its own. Deletion happens only through the Jmodot PR merge `/merge_pr` runs (`gh pr merge --delete-branch`) or on an explicit owner word; otherwise notify the user that the paired branch and PR await cleanup.
9. **Push the submodule BEFORE publishing the parent ref that points at it.** A cross-repo landing is an ordered pair of irreversible pushes: Jmodot first, then the parent. Done when, after `git -C Jmodot fetch origin`, `git -C Jmodot branch -r --contains <the commit the parent gitlink names>` lists a remote branch, before the parent ref moves (`ls-remote` lists ref tips only, so it misses a published commit after its branch advances). Order: `git -C Jmodot push`, then `git add Jmodot`, then the parent commit and push. The pointer bump is a feature-branch step, never taken after the Jmodot PR merges (see the merge-order rule). Worktrees share the parent's refs, so moving `main` onto a gitlink naming an unpushed Jmodot commit breaks every other checkout reading that ref, and the error names the POINTER, not the absent push. No hook enforces the order; the packet approving the parent push shows that `branch -r --contains` proof.

10. **`git mv` from {{PROJECT_NAME}} into the submodule path dual-tracks.** `git -C <{{PROJECT_NAME}}> mv <project-path> Jmodot/<sub-path>` stages the moved files at `Jmodot/` *in {{PROJECT_NAME}}'s index* (`RM`/`R`) and the `Jmodot` gitlink as **deleted** (`D Jmodot`); the submodule sees them **untracked**. Untangle before committing: `git -C <{{PROJECT_NAME}}> reset HEAD -- Jmodot/<paths>`; `git -C Jmodot add <paths>` and commit on the branch rule 1 names; `git -C <{{PROJECT_NAME}}> add Jmodot`. Done when {{PROJECT_NAME}} stages only the source-side deletions plus a `160000`-mode pointer bump. Cross-repo moves don't preserve file history; carry each `.cs.uid` in the same mv so Godot uid resolution survives `--headless --import`.
11. **Jmodot has no gate of its own.** Its tests run in `Tests/Logic/JmodotTests`, so the consumer's full gate over the tree holding both commits backs the framework commit, which lands first (rule 9).
