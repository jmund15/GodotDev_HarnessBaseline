# Sidecar Dispatch — one recipe, every transport

A sidecar is a separate client process on a chosen transport. `orchestration` §0 owns route selection: a job on the session's own plan runs as a native Workflow agent, so this recipe covers jobs on any other plan and jobs whose fields need process isolation. Claude-client launchers use `scripts/lib/sidecar_common.sh` for flags, disclosure and recovery. A native-CLI seat runs a vendor's own CLI with its own permission configuration: the OpenCode seat (`opencode run`) and the Antigravity seat (`agy` on a Google plan, one transport per quota bucket: Gemini, Argon, Claude), where the project ships them. The Antigravity seat writes a `.agents/` workspace into a run root of this project, so agy loads the CLAUDE layers, the memory index, the skills, the tool, SessionStart and Stop hooks (amendment delivery included) and the read-only MCP servers. Use each seat's flag validation rather than assume Claude-client disclosure, hooks or resume support; the job file is the same as any other. The disclosure, tool-profile and permission sections below, and `reference/sidecar_runs.md`'s resume section, describe Claude-client launchers.

## Procedure

1. **Model ladder:** the read-before-pin rule is `orchestration` §5; `hooks/sidecar_dispatch_context.py` denies a launch while the session has not read the ladder since compaction, naming the load route.
2. **Roster + launcher:** `python3 .claude/tools/model_registry.py available` — prints available aliases, roles, effort evidence and paying-plan launchers. Effort displays measured effort levels or an evidence label. Dollar input rates appear only for priced non-plan-quota rows. Launcher = the `launcher` of the plan you chose to pay; `available` names each row's plans and their launchers, and `for-role` names only the plans, never their launch lines. A plan may share another transport's models (`planOf`). The session's own plan runs native; any other plan runs through its `launcher`. Excluded models are out; re-select under the ladder (`reference/model_ladder_evidence.md`) — **a stale route name in a command is not a reason to fall back to the session's own transport.**
3. **Dispatch facts + live capacity:** run `python3 .claude/tools/dispatch_size.py <jobs.json>` and `python3 .claude/tools/sidecar_fanout.py <jobs.json> --dry-run` on the jobs file from step 5. They print each job's pin, brief bytes and estimated tokens, and the plan the fan-out would pay. `<launcher> --check -m <alias> -e <effort> -G <kind> -f <prompt.md>` stays a setup and availability check: it prints the requested pin, the kind's tier mapping, the matching ladder row with its effort and the latest rating for that kind's guard and model with its note (or none), then reads the current seat's plan band and the target provider's normalized quota/balance before any model request. A preflight refusal exits before any model request and names its condition; `reference/sidecar_runs.md` §Exit codes owns each code. A plan-quota window never refuses on a pressure ceiling; which plan pays is your choice by the model ladder's selection line. `-A` overrides only the host-band floor. The dispatch hook runs the `--check` preflight on a direct launch and denies on any refusal. Before it, the hook runs the Workflow route's tier check (`hooks/_dispatch_checks.py`) on the launch and on each fan-out job: a kind whose tier the alias's row does not serve is denied. Each plan's quota left against its window left is the `[budget-posture]` line, and a row's owner probation mark prints on `model_registry.py for-role <tier>`; both are read before the pin.
4. **Prompt to a file** (never argv — Windows argv caps at ~8K). Schema to a file when you need structured output.
5. **Dispatch** — one route for one job or many: a jobs file run by `python3 .claude/tools/sidecar_fanout.py <jobs.json> --detach` in a foreground call. One job is the one-element file `[<job>]`. The launcher owns every per-job gate (memory, observed capacity, the quota-window fit). A job the fit forecast does not hold warns and runs; only a caller that sets `SIDECAR_CAN_WAIT=1` (the bench grid) waits there for room, and a spent plan stops at observed capacity. The fan-out maps job fields to launcher flags: `alias` + `effort` or `rows` → `-m` and `-e`, `kind` → `-G`, `tier` → `-Q`, `promptFile` → `-f`, `label` → `-l`, `workdir` → `-d`, `contextFiles` → `-C`, `longContext` → `-M`, `schemaFile` → `-S`, `tools` → `-t`, `pick` + `spec` → `-Y`. It adds `-X`, `-R` and `-P` itself, and its `--authorize` flag is `-A`. Any other launcher flag goes in the job's `extraArgs`; a job with `extraArgs` or `tools` falls to normal permission, since auto-approval covers only `SAFE_JOB_FIELDS` (`hooks/sidecar_dispatch_context.py`). An unattended script that calls a launcher directly passes `-R` and `-l` as literal values: tracking reads them from the command text, and an unresolved variable or loop-carried value is denied.

After `-R` is parsed and its directory remains writable, the launcher's EXIT trap writes `<record>.exit`. Captured output writes `<record>.out`. Detached stdout redirection can create that file empty before the child runs. File existence alone is not captured output. Errors before a valid `-R` may create neither file. A launch ending after its label or `-R` is parsed writes a spend-ledger row unless its resolved ledger path is empty (`-L ""` disables the row). The row uses the published record, or `outcome: ended-before-result` with its exit code and refusal line when no result exists (`finished-without-record` for a finished run without `-R`).

A detached job outlives the session and its own launcher exit is not the run's: watch it with step 6's command, and inspect the process and record before any kill. Each `-R` path takes one launch: a path whose `.out`, `.err`, `.exit` or `.pid` exists refuses with exit 1.

6. **Watch — one route for every sidecar, Workflow, bench campaign and long Bash background job.** Arm one session watcher when none of yours is armed: run `python3 .claude/tools/watch_records.py --session --wake` with Bash `run_in_background` and `timeout` 7200000 (the default 30-minute limit ends it before its check-in). Issue a launch and its arm in one message so both calls share one request. A session watcher waits for the launch entry, then exits `NONE` once nothing it watches is live; `--await-launch` is unnecessary. A re-arm after a wake takes no flag. Do not arm beside a live watcher. A racing duplicate waits to take over instead of exiting and spending a wake on bookkeeping. It re-reads this session's pending sidecars, running Workflow runs, live bench rosters and running Bash background tasks (a task with no end notice counts as live work, so its check-in lands inside the cache window) each poll and wakes you when one
   needs a decision (`reference/sidecar_runs.md` §Detached runs, *What wakes you*). A watcher whose session can no longer receive a wake ends by itself, printing `HOST GONE: <reason>`: its parent shell or the session host that owns it is gone (read from the client's session registry; a client that writes none is never ended on a guess). On a wake, act on its output without a tail or cat call, then re-arm: it carries every job that ended since the last wake (a sidecar, a fan-out job, a Workflow run or a background shell) with its exit, result head, report path and verification counts, then an `UNRATED` line. Decide wake units at launch time: the jobs of one fan-out call wake you at
   the last clean end, because each wake re-reads your whole context. A failure wakes you at once, and a clean end held for the
   group prints at the next wake, at the latest the watcher's check-in. Give a job `"wakeWith": "alone"` when its result is
   actionable before the others end (review it, merge it, launch what it gates, triage its offers). The fan-out groups a jobs
   file with a top-level `measurement` (the comparison its jobs make) and its `lens` and `reviewer` jobs by itself, and
   makes an `author` alone, since its written result is integrated on its own; give other jobs one `wakeWith` group name to wake a subset
   together. Jobs whose results gate a later job are separate fan-outs, and you start the next when you wake. The Stop hook blocks while a running sidecar, a live bench roster or a running Bash background task this session started has no live watcher unless the payload already sets `stop_hook_active`. When a stopped notice arrives for a backgrounded launch with `-R`, read `<record>.exit` first.
   **Pane, the owner's live view.** Issue `python3 .claude/tools/watch_records.py --pane` with Bash `run_in_background` and `timeout` 86400000 in the same message as a session's first arm, and again when a wake's last lines carry `PANE none`. It appends the running jobs' check-in lines each time they change, so the owner sees the latest state at the tail of that background shell in the CLI and desktop clients; mobile shows no running shell's output. Leave it running and unread: it ends only by `HOST GONE` (a watcher also exits on a wake), and the watcher does not count it as live work (its docstring owns the behavior).

7. **Consume:** the wake's result head opens the answer; for the whole of it, wait for `<record>.exit` (or prove the process gone), then read
`<record>.claims.json`: its `result` holds the answer and its `claims` carry applied verdicts.
The host writes it and `<record>.post_check.json` before publishing a job's record or
completion, on ordinary and detached paths. Read its `verification` under
`commands/agents/orchestrator_action_protocol.md` Step 1.5; an `unavailable` report is UNCHECKED. The Stop audit reads the same
checked file. `<record>.out` remains unchanged captured stdout for diagnosis, not consumption;
`-o` names its format, not a path. The fan-out gives every job a `-P` progress stream, which selects stream-json for compaction/transient recovery. A gate refusal with no captured
output means no answer, not a successful empty review. The `-R` record holds `costUSD`
(list-price tokens; `costBasis` says whether it is spend or a plan-quota comparison figure; never `total_cost_usd`: that payload is inflated and no divisor corrects it), `servedModel` and attestation; `tools/run_cost.py` prices any record or result the same way. Rating follows `/orchestration_metrics` §Incremental rating.
If a completed review's fold failed, run `sidecar_fanout.py <jobs.json> --out-dir <finished-run> --refold` with its `--fold-*` and `--ledger-*` flags: it dispatches no seat and keeps prior artifacts (tool usage owns attempt paths).

The route is `tools/sidecar_fanout.py`, which detaches every child with `-X` so killing the fan-out's own process stops none of them. `--detach` in a foreground call validates, hands the sidecar jobs to a detached driver and returns, and the step-6 watcher wakes you. Jobs it placed on the session's own plan are not launched: it prints one `NATIVE` line holding the `Workflow` call (`args.jobsFile` = `<out-dir>/native.args.json`) for you to issue, and with no sidecar job left it starts no driver. The pacing, `maxChildren` and `--max-parallel` rules below bound the sidecar jobs only; the native count is bounded by `orchestration` §5b's one-native-job rule. A job whose named plan has no room, or whose route has no plan with room, is refused in that call, by the dispatch hook from cached capacity and by the planning pass. A review seat (`lens` or `reviewer`) whose reading (brief, context, must-read and named files) is past its pin's usable window is refused in that call too, naming the job, its reading and its window; `dispatch_size.py` prints it as `preflight: unmet`. A file the launcher opens (a job's brief, schema or context file, the shared `contextPath`) that is no file under the launching checkout is refused before anything spawns, naming the job, field, path as written and root, and prints as `preflight: unmet` too. Any other job past its window launches: its `fit:` line states the overage, since it compacts and carries on. The call returns when each first-wave job is printed `admitted`, `refused`, `queued` or `undecided`; the wait is the launchers' own start, so it grows with the jobs starting at once. Every readable plan is paced, so a forecast-only shortfall queues jobs instead of refusing them. Each job end and each launch decision re-reads the plan's capacity. A job launches while every window the plan states holds its drain beside the running jobs. Each window is priced by its own history, because a short window and a weekly one are different units. A plan with nothing running always takes a job, a transport that declares `maxChildren` in the registry holds that many child CLIs at once, and a caller-set `--max-parallel` bounds the total (default: none). A queued job's line names what held it. Once a job has ended and a window's reading has moved, the observed drain per job replaces that window's forecast for the plan's remaining jobs, scaled by each job's own forecast. A job its plan cannot hold moves to a route sibling that holds it now (a job with a named `plan` never moves), else waits for a running job to end. A plan that reads spent, or whose job ends with a usage limit, moves its unstarted jobs to a route sibling with room, else leaves them `not run` with the reset time. A job with no named `plan` that a usage limit stops mid-run continues on a plan that holds it (`reference/sidecar_runs.md` §Provider usage limit). A job may list every row that meets its bar as `rows: {"<alias>": "<effort>", ...}` in place of `alias` + `effort`; giving both refuses. A check-scored job records `spec` and gives each row `null` (`rows: {"<alias>": null, ...}`): the fan-out fills each row's computed effort (`orchestration` §5 *Effort*), and each listed row is validated as `alias` is, its tier included. The fan-out applies the ladder's selection line step 2 (`reference/model_ladder_evidence.md`) across those rows' plans and runs the winning plan's cheapest listed row with that row's effort. A move or launch fallback switches alias and effort to the next plan's cheapest listed row. Which rows meet the bar stays your judgment. The admission line names the row (`plan <plan>, row <alias> (<effort>)`) and the run record's `requestedModel` names the row that ran. A job listing one row gets a `spare plan:` line when another plan serving its tier projects unused quota. A window projects none when it has more time left than it has run (its rate was measured over less). A stale or unreadable reading decides nothing, and a queued job still meets its launcher's capacity gate when it starts. A driver held in a backgrounded Bash call ends at the tool's background limit, stranding its queued jobs and its `<label>.md` writes, so run it with `--detach`. Capture bytes do not prove a run ended: a retry waits for that run's `EXIT` file, or for its process to be proven gone, and takes a new `-R` path. The fan-out's jobs file may be a `dispatch.js` args file (its docstring owns the job spec). A job's final message writes `<out-dir>/<label>.md` only when a final message exists and the write succeeds. The parent treats an absent required artifact as uncovered. A claims fan-out skips child launcher checks, verifies once with `--root <subject-root>`, and publishes `post_check_claims.json` and `claims.json`; consume `claims.json` after the driver finishes, not the raw spills or event stream. For jobs without claims, consume `<label>.md`. Several jobs run at once receive `dispatch.js`'s single-flight guard as a `-C` file.

A review panel is `sidecar_fanout.py <jobs.json> --review --detach` (jobs from `lens_briefs.py prepare`, or `--target sidecar --plan <review_ledger.py plan output>`). The fan-out places its seats like any other jobs: a seat on the session's own plan is the `NATIVE` Workflow call it prints, the rest are sidecars. A panel with no native seat wakes you once, at the fold's end, with no `wakeWith`, since the fan-out runs the post-check and fold after the seats. A panel with a native seat is closed by the call the fan-out prints: `sidecar_fanout.py <jobs.json> --review-close --workflow-dir <transcriptDir of each NATIVE call>` plus the run's `--fold-*` and `--ledger-*` flags. It lands each native seat's result and its agent transcript beside the sidecar seats' files, so the one tail below judges every seat the same way, and it refuses while a sidecar seat still runs. A seat records each finding with `tools/seat_findings.py` beside its brief as it settles it (its brief names the command), so a structured return that fails to parse loses none: the tail reads a failed or absent return's recorded rows in its place, with the same coverage checks, and prints the seat's line with a warning that its structured return failed and names the findings file. A caller whose seats carry their own brief files writes the jobs file itself: one job per seat `{label, mandates: [<seat key>], mustRead: <lens_briefs.py must-read entries>, alias: <registry row>, promptFile, tier, effort, kind: "reviewer", schemaFile: ".claude/schemas/review_findings.json", workdir: <repo root>, contextFiles: [<shared context file>]}`. It writes `review.json`: every seat's coverage, source F-ids, exact same-file same-claim M-id groups and quote verdicts. `--review-artifact <review.json> --select <F-or-M-id>` returns the one held finding it names, with its original contributors. Adding `--fold-alias <alias> --fold-effort <effort> --fold-subject <root>::<snapshot manifest>::<file>[,<file>...]` (repeatable) launches one author per subject that received findings, working in the subject's `root`, and follows `commands/agents/review_fold.md` (`--fold <template>` names another brief); `--ledger-stage`, `--ledger-subject` and `--ledger-roster` record the panel. Every `--review` run, folded or not, ends by running `tools/post_check.py review` in-process and writing `post_check.json`, in which `tools/fold_check.py` decides each folded subject. Consumption follows `commands/agents/orchestrator_action_protocol.md` Step 1.5.

## Job kind

A job declares one `kind`: `-G <kind>` on a launcher, `kind` in a jobs file, a Workflow job or a native command. The kind's row in `guards/tool_profiles.json` sets built-ins, MCP servers, disclosure, delegate guard, agent type and tier, and `tools/tool_profiles.py` resolves it. This section holds the choice and no copy of the row's columns.

| kind | fits | litmus |
|---|---|---|
| scout | locate, enumerate, extract | the answer sits in files and needs no project doctrine |
| lens | a survey that must dodge known traps | scout work that needs `MEMORY.md` |
| reviewer | red-team, plan check, verdict lenses | the output is a verdict on a plan or diff |
| author | code or doc authoring, TDD under a spec | the job writes files |
| judge | judgment fitting no other row | none of the rows above fits |
| gate | the wide run every other kind is refused | a whole suite, a regression gate, or a batch that reproduces a crash |

The read-only picks carry read-only git (the `git` MCP server: log, show, diff, grep, status, blame, ls-files, rev-parse, merge-base, branch listing, for-each-ref, rev-list), and withhold `mcp__ai-worker__write_doc` (`denyTools`); `author` keeps it.

Tools by kind: `scout`, `lens`, `reviewer` and `judge` hold `Read`, `Glob`, `Grep` and `Bash`, so any of them runs a report tool or a git command; none holds `Edit` or `Write`, and a prompt line bars writing through the shell. `author` adds `Edit` and `Write`. `gate` holds `Read`, `Grep` and `Bash`. The kinds differ in the doctrine they load and in write access, never in whether a command runs; `-t` stays for a removal or an MCP server. A native job whose delta changes what its kind's row holds refuses without a `variants` agent file. A row with `internal: true` serves a harness driver and is never a pick.

Pick the lowest kind the child's work needs, on every model. A `scout` or `lens` child's measured first-turn load is about 17–25K tokens and a `reviewer` or `author` child's about 29–37K, by launcher (no `judge` measurement); the child pays that load every turn, it takes window room, and on a row with a long-context price step it can push a request past the step.

Effort follows the ladder cell for the role and work shape. A `see-ladder` row names that home instead of an effort level. Treat an `unmeasured` row as a guess, not a defensible pin. Legal `-e` values come from `model_registry.py effort-values <alias>`: the row's declared values narrowed by the transport's vocabulary, or the transport's values when the row declares none.

**The kind sets disclosure, so size it against the window.** A readable child transcript supplies `turn1ContextTokens`/`turn1ContextPct` in `-R`. Unavailable measurements are null and print no context line. Do not substitute an estimate for an observation. Size the kind against the receiving model's observed first-turn context and usable window; choose `scout` or `lens` unless the work requires full doctrine. Split or narrow inputs when they will not fit. The brief is the bigger lever — hand paths and Grep targets, never the input.

## Optional flags

`-C <file>` extra context (repeatable) · `-a <dir>` extra read grant (e.g. the vault) · `-t <csv>` signed tool delta (§Tool profile) · `-B <csv>` an `arm` job's task built-ins · `-p <mode>` permission mode (default by transport, §Permission mode) · `-P <file>` live progress stream (do not redirect the canonical Bash command; redirection defeats its narrow approval) · `-T <sec>` wall-clock kill (default OFF; the run is killed with exit 124, so pass it only when you can name why) · `-Z <sec>` stall signal on the `-P` stream (set above the longest silence seen on healthy runs of that transport, and pass it when that silence exceeds the default `SIDECAR_STALL_SEC` in `scripts/lib/sidecar_common.sh`; 0 off; a run silent that long appends a `stalled` journal row and keeps running) · `-r <id>` resume a persisted session · `-K <tokens>` the Anthropic child's compaction window, 100000..1000000 (`reference/sidecar_runs.md` §Compaction specifics) · `-M` long context past a row's long-context price step, refused on a row without one; it holds the max window for the whole run, so pass it only to resume (`-r`) a run already past the default window, never on a fresh job (`reference/codex_session_runbook.md` §Launch) · `-W` dispatch inside a peak pricing window on a `gate.peakPolicy: refuse` row. Pass `-W` only when the user explicitly authorized peak pricing in the current conversation; `-A` does not cover it.

`-C` is appended as **SYSTEM instructions**, not a passive data attachment. When a reviewer must judge a plan or rubric as data, label it DATA and blockquote its lines.

### Tool profile

`guards/tool_profiles.json` is the one table (a `kind` maps to its built-ins and its logical MCP servers); `tools/tool_profiles.py` is the one resolver every launcher, `tools/sidecar_fanout.py` and the Workflow hook read. Each launcher passes `--tools`, `--strict-mcp-config` and `--mcp-config` from that resolved profile, and `-R` records it as `toolProfile` (`kind`, `tier` when the kind row names one, `builtins`, `mcpServers`, `add`, `remove`, `overrideMode`, `enforcement: strict`, `mcpRegistrations`); `orchestration_metrics` archives the record's `toolProfile.tier` and `parentSessionId` as the row's role tier and session.

`-t` is a signed delta (`+Bash,-Grep,+mcp:godot`). A Workflow job takes a signed string or list, or a structured `tools.add`/`tools.remove` delta. An unsigned or malformed value refuses rather than losing a requested grant.
Only for `-G arm`, the task row supplies the arm's built-ins. `-B <csv>` carries that row
when a cell also adds a delta: `-G arm -B Read,Glob,Grep -t +mcp:ai-worker` is legal,
while `-G arm -t +mcp:ai-worker` alone is not. An unregistered server, unknown kind,
invalid removal or mixed CSV refuses before spend.

**A dispatch is never granted `Workflow` or `Agent`**: orchestration stays with the calling session. The CLI could grant them, so this is policy: the resolver refuses both in any `-t`, delta or arm task row (`RESERVED_BUILTINS` in `tools/tool_profiles.py`). The one exception is the `bench-score` row, the score daemon's driver, whose whole job is one `Workflow(score_cell.js)` call.

## Permission mode

Provider-transport children launch with `bypassPermissions`: on those seats the auto-mode classifier runs on the provider model through the proxy and denies ordinary scratch and test writes. Under bypass, project hooks (heredoc, kill, harness-edit, gate cadence, dispatch guards) and settings deny rules still decide. Evidence: vault `DevProjects/{{PROJECT_NAME}}/Claude/Meta/Benchmark/harness-guidance-2026-09/permission-mode/`. The anthropic transport keeps `auto`. Pass `-p` only to override a default for a stated reason; never pass it to retry an action a hook or a deny rule refused.

Every child also gets the **autonomy rail** (`sidecar_common.sh` `sc_build_disclosure`, all tiers, all models): it runs unattended, never ends on a question, decides and states the assumption, reports a blocker inside the deliverable. At consumption, the parent rates a question-only final message as no delivery.

Never: `-n` (a turn cap discards a paid run) · an unverified `CCP_BIN` override (`environment_bootstrap` owns the machine detail) · a pin from ANOTHER transport's vocabulary inside Workflow `agent()` — role names on a provider session, vendor ids on an Anthropic one. Pin the session transport's own ids; `hooks/workflow_provider_guard.py` denies the other and names the roster.

## After launch

`reference/sidecar_runs.md` owns what happens once a run starts: resume, provider usage limits, compaction internals, detached-run wakes and exit codes. Read it when a run ends, refuses, stalls or wakes you. Its rules that shape the brief at launch:

- Pass the brief path absolute and native: the re-prompt hook opens it from the child's cwd, which is a worktree or a temp dir.
- A job whose `-d` is a linked worktree cannot Write, Edit or NotebookEdit into the main checkout: `hooks/sidecar_workdir_guard.py` denies it, except under the job's spill dir (the directory of its `-R` record) and the paths its brief's `task` block `writeSet` names. Declare every main-checkout path the job writes in that `writeSet`, and put its report under the spill dir. The brief itself is never writable, wherever it sits. A Bash command with a clear write there (a redirect, `tee`, a `cp`/`mv`/`install` destination, `sed -i`, a mutating `git -C <main>`, a python path literal beside a write call) is denied the same way; a target it cannot resolve statically is allowed.
- Name the brief's on-disk outputs and ask for partial output early: that is the resume path.
