# Design litmus

Ten questions, asked when you introduce a type, an authored setting, a parameter, a behaviour switch or a helper. The doctrine behind them is `architecture_philosophy`; this file holds only the question each introduction must answer. Authored code only, not generated or vendored code. Other files cite the questions by number.

1. **Reuse before introduce; a seam needs a second implementation or consumer.** Before adding a named configuration surface, name the family that already owns the concern, or record that none exists. A bool that selects behaviour is a strategy slot in disguise: look for a strategy or config family first. Passing a literal null or default into a parameter typed as an existing strategy is a neutered seam: wire the family. *Reverse case:* before writing a retry, deferral, queue, cache or guard inside one consumer, name every other consumer of what it wraps; more than one means one owner, never a copy each. *Dual case:* a seam cut for exactly one implementation is indirection; name the second implementation or consumer that exists today, or that the owner stated as direction, or do not cut it. Schedule pressure does not change this order; a smaller change is offered as a choice, never shipped silently.
2. **Is this a new axis?** Behaviour on a different axis from the base's is composed, not subclassed (`architecture_philosophy` §Extension shapes). A type switch needs a closed set.
3. **Does this knob change one thing?** Its name describes everything that flips with it (§Authored data is an API).
4. **Does this value already have a home?** Derive it there; never author it twice.
5. **Is every visible setting read** in every context an author can reach it? An inert setting is a defect: wire it, narrow it per context, or delete it when an existing mechanism supersedes it.
6. **Cohesion.** If this piece were deleted, would exactly one responsibility disappear? More: it is fused. Less: it duplicates an existing surface. This asks what the piece owns; the Deletion Test asks whether it is deep enough to keep.
7. **A seam is signature plus contract.** For an interface, abstract base or component contract, state its invariants, call order, failure modes and required configuration beside its members: initialization order, subscription order and required-dependency loudness are exactly what a signature cannot carry. *Litmus:* could a caller holding only the signature use it wrong and still compile? *Order is the last resort:* before documenting a call order, name what would make the wrong order impossible (derive the state instead of storing it; do the work where every input exists). A two-step protocol has two half-implementations that both compile. A consumer forced to invent an input shows the seam varies the wrong thing.
8. **Reader load has two axes:** layers to trace and state to hold. A flat file with fifty globals is as hard as a six-layer adapter stack. *Litmus:* can a new reader answer "where does X come from?" and "what can change X?" reading straight through?
9. **Organised by when it runs is a defect.** A module split into initialize, validate and apply passes question 6 while still being the defect. *Litmus:* what would it own if execution order were free?
10. **Count the author's actions for the common case.** Type each authored slot to the narrowest base, prefer a typed list of pairs over a loose map, and default the common case: the number of steps for the most frequent edit is the number to minimise.

**Gating:** gate on the event, not an output magnitude; a transition's order can hide a gate; latch only after its operation succeeds.
