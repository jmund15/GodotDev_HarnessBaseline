# Model Ladder

The model table. Load it whenever you pin a model or an effort.

- **Owners elsewhere:** dispatch rules are `orchestration` §5; tier claims are registry `roles`; availability is `reference/external_models.json` (`python3 .claude/tools/model_registry.py available`); launching a sidecar is `reference/sidecar_dispatch.md`. An unavailable model is out: pick again from what remains.
- **`evidence`** tags each row's sources: `pub` published vendor or independent results, `bench` our battery, `use` owner rulings and real use. No source gates a pin.
- **Rows name product-line families.** A row covers every registry row of its family on any transport, and `scout pool` covers each family it lists. Dispatch a model no row covers only by the alias the user names, never as a substitute chosen by rule.
- **Detail behind a row** is in the Obsidian vault: `bench` on `Claude/Meta/Benchmark/model-effort-v1.0/RESULTS-BOARD.md` (`TASKS.md` beside it maps each work shape to its task), `pub` in `Claude/Meta/Benchmark/ladder-ingest/pub-evidence.md`. The table settles every routine pick; read the detail only for a question about the ladder itself.

## Role definitions

Five tiers, named by work shape. `python3 .claude/tools/model_registry.py for-role <tier>` prints the rows whose registry `roles` claim that tier. A stronger row does not claim lower tiers by default; check its `±` cell before using it for another work shape.

A tier a row lists in registry `supplementary` lets it take an added review seat beside qualified seats that together carry every mandate; it covers no mandate alone, even when `roles` also lists the tier (the row then also authors at it). `for-role` and `provider_bands.py lean` list a row apart when it holds the tier only there.

| tier | work shape |
|---|---|
| `orchestrator` | scoping, dispatching, reviewing across systems; long-horizon sessions; the final cross-system design verdict |
| `architect` | solution design at any scope: fresh and scoped architecting, planning from a thin or thick design, design and plan review |
| `executor` | implementation and verification under a scope: coding, root-cause debugging, fix authorship, red-team of a concrete artifact |
| `fanout` | read-heavy and mechanical work: surveys, enumeration, text comparison, rubric checks, tight-spec execution |
| `scout` | locate / enumerate / extract, verifiable without applying project doctrine |

`validation` is not a tier: it is the `fanout` row at a lower effort.

Terms the cells use:

- **fresh architecting:** design with no existing design to extend. **Scoped architecting:** one change inside an existing system.
- **thin-spec planning:** the planner settles open design choices. **Thick-spec planning:** the design is settled; the plan sequences and covers it.
- **tight-spec execution:** the spec states every behavior. **Loose-spec execution:** the spec states the goal, not the means. **Converged work:** only execution remains. **Ambiguous execution:** the executor must judge a result no check scores (`orchestration` reference `slice_pins.md`).
- **oracle:** a mechanical check that scores the result (a test suite, a golden file). **Parity refactor:** a restructure an oracle proves behavior-identical.
- **survey** or **explore lens:** a wide read that locates and sums up across many files; a missed item is its failure. **Chained research:** each answer feeds the next question. **Mechanical fan-out:** extraction, enumeration, text comparison, and a verdict per item against a written rule (a rubric check). **Lens:** one narrow review pass with a stated check; an **anchored** lens is handed the artifact and the check.

## Role guidance

`effort` gives the starting effort per work shape; `orchestration` §5 *Effort* says when to raise or lower it after a result. `±` says why to pick the row (`+`) and why not (`−`). Read a cell as evidence, never as the pin: name the job's demand first (how open and deep it is, and whether a check scores the result), then place each row on it. A range starts at its low end only where a check scores the result, so a shortfall shows. Without one, start where the job's depth puts it; open-ended work (fresh design, ideation) takes each row's top listed effort. A shape a row's cells do not name: judge it from the row's intel and its nearest named shapes, and a row weaker there takes more effort, not less; never bar it. A `±` limit binds only on the shape its evidence measured.

- **You choose every pin; no tool chooses it.** Tools drop only rows that are wrong in every case (no tier claim, unavailable, a plan refused on capacity). No listing order or advisory is a pick. The one pin a tool fills is an engine's own checked step (`orchestration` §5 *Effort*). Weigh the rest in one pass:
  1. **Fit sets the floor; the job's bar sets how much quality to buy above it.** A row clears the floor when its registry `roles` claim the tier; its `±` cell says how it fares there. The owner's stated preference (cost-effective or maximum quality), the owner's lean condition (`orchestration` reference `spend_lean.md`) or the work's rigor sets the bar. With none stated, quality leads where it decides the result (architecting, design, an in-depth defect-hunting review) and cost leads elsewhere (execution under a settled spec, fan-out including per-item rubric verdicts, extraction). Where rows match on the shape, a stronger row buys nothing. A board lead inside the judge band is no quality difference.
  2. **Plan, then price.** Quota unused at a plan's reset is lost, so spending it costs nothing. Among plans with a row that meets the bar, take one whose `[budget-posture]` entry shows quota going unused at reset, the earliest reset first; with none, the one with the most room (quota left against window left). On that plan, take the cheapest row that meets the bar: the `cost` cell compares rows on one plan only, since two plans' quotas are different currencies. Neither unused quota nor room buys a costlier row; the bar sets quality. Speed breaks ties.
- **Review seats:** step 1's floor applies, and a `supplementary` row clears it for an added seat beside a qualified one. Among rows that clear it, prefer a provider other than the subject's author when that provider's plan has room. The preference never adds a seat.
- **Session vs delegate:** at equal intel the lower-`deleg` row is the better delegate. Pair an orchestrator-row session with architect- and executor-row delegates.
- **`agentType: 'Explore'`** works with any model pin and loads no project doctrine, cutting first-turn input by about a third. Use it only for read-only locate/enumerate/extract lenses, never one that must apply project rules.
- **Compaction:** a pin's compaction point (`model_registry.py usable_window`) bounds a job's whole working set: the subject it keeps resident, its reads and its reasoning. A lane of independent items compacts and carries on. A job that must keep one subject resident (a review seat, a design, a plan, chained research) and outgrows the point can lose the subject at each compaction and cycle: give it a narrower mandate, a smaller subject, or a row whose point holds it. Every Claude dispatch, sidecar or native, compacts at the smaller of its model's window and the login's `autoCompactWindow` (`model_registry.compaction_point`), so a subject over a row's point needs a row whose point holds it. A sidecar job that must read a large subject in once and then works only a few turns may set `window: "full"` to compact at its model's own window; every later turn re-sends the whole context, so a job with many turns past the login's point costs more with it. A native agent always takes the login's window. A proxied agent compacts only on an adapter build that detects the client's compaction control.

## Axis definitions

Higher = better on every axis. `?` = no evidence yet.

- **intel:** the hardest problem handled unsupervised.
- **deleg:** orchestration ability (scoping, spec-writing, dispatching, reviewing returns, holding a long plan); it decides who runs a session. `—` = never a session model.
- **taste:** UI/UX, code cleanliness, API design and prose, relative to the owner's preference.
- **speed:** time to completion.
- **cost:** what one result costs at the row's price (registry `price`). On a plan row it weighs quota draw, not money.
- **billing:** vendor · how a call is paid: `plan` spends a subscription quota, `pay-as-you-go` spends money per token, `free` spends neither.
- **effort:** the starting effort per work shape, for `agent()` pins and the session `/effort`. A result at one effort shows it is enough, not that the others fail. An effort the row's registry `effort.avoid` lists is never pinned outside a `sidecar_fanout.py --compare` run or a benchmark campaign file; the guards enforce it. `—` = no effort setting.

Harness load is a third pin beside model and effort: `orchestration` §5 *Per-dispatch harness cost*.
