# Model Ladder

The model table. Load it whenever you pin a model or an effort.

- **Owners elsewhere:** dispatch rules are `orchestration` §5; tier claims are registry `roles`; availability is `reference/external_models.json` (`python3 .claude/tools/model_registry.py available`); launching a sidecar is `reference/sidecar_dispatch.md`. An unavailable model is out: pick again from what remains.
- **`evidence`** tags each row's sources: `pub` published vendor or independent results, `bench` our battery, `use` owner rulings and real use. No source gates a pin. The battery's execution tasks (tight- and loose-spec execution, debugging, parity refactor, test authoring) all run in one Godot C# codebase, so a `bench` claim about those shapes is measured there; weigh it as weaker evidence for work in another language or domain.
- **Rows name product-line families.** A row covers every registry row of its family on any transport, and `scout pool` covers each family it lists. Dispatch a model no row covers only by the alias the user names, never as a substitute chosen by rule.
- **Detail behind a row** is in the Obsidian vault: `bench` on `Claude/Meta/Benchmark/model-effort-v1.0/RESULTS-BOARD.md` (`TASKS.md` beside it maps each work shape to its task), `pub` in `Claude/Meta/Benchmark/ladder-ingest/pub-evidence.md`. The table settles every routine pick; read the detail only for a question about the ladder itself.

## Role definitions

Five tiers, named by work shape. A stronger row does not claim lower tiers by default; check its `±` cell before using it for another work shape.

A tier a row lists in registry `supplementary` lets it take an added review seat beside qualified seats that together carry every mandate; it covers no mandate alone, even when `roles` also lists the tier (the row then also authors at it). `for-role` lists such a row once with `supplementary` standing beside the qualified rows.

| tier | work shape |
|---|---|
| `orchestrator` | scoping, dispatching, reviewing across systems; long-horizon sessions; the final cross-system design verdict |
| `architect` | solution design at any scope: fresh and scoped architecting, planning from a thin or thick design, design and plan review |
| `executor` | implementation and verification under a scope: coding, root-cause debugging, fix authorship, red-team of a concrete artifact |
| `fanout` | read-heavy and mechanical work: surveys, enumeration, text comparison, rubric checks, tight-spec execution |
| `scout` | locate / enumerate / extract, verifiable without applying project doctrine |

`validation` is not a tier: it is the `fanout` row at a lower effort.

Terms the cells use:

- **fresh architecting:** design with no existing design to extend. **Scoped architecting:** one change inside an existing system.
- **thin-spec planning:** the planner settles open design choices. **Thick-spec planning:** the design is settled; the plan sequences and covers it.
- **tight-spec execution:** the spec states every behavior. **Loose-spec execution:** the spec states the goal, not the means. **Converged work:** only execution remains. **Ambiguous execution:** the executor must judge a result no check scores (`orchestration` reference `slice_pins.md`).
- **oracle:** a mechanical check that scores the result (a test suite, a golden file). **Parity refactor:** a restructure an oracle proves behavior-identical.
- **survey** or **explore lens:** a wide read that locates and sums up across many files; a missed item is its failure. **Chained research:** each answer feeds the next question. **Mechanical fan-out:** extraction, enumeration, text comparison, and a verdict per item against a written rule (a rubric check). **Lens:** one narrow review pass with a stated check; an **anchored** lens is handed the artifact and the check.

## Role guidance

`effort` gives the starting effort per work shape; `orchestration` §5 *Effort* says when to raise or lower it after a result. `±` says why to pick the row (`+`) and why not (`−`). Read a cell as evidence, never as the pin: name the job's demand first (how open and deep it is, and whether a check scores the result), then place each row on it. Compare (row, effort) cells whole: one effort name buys different work on different rows, so never move the row and keep the effort. A check-scored job's cell lists one effort, and a tool computes the effort from it, starting at that cell and climbing only on failure, because the check shows a shortfall. Judged work, which no check scores, takes its effort from the cell's range, where its scope, complexity and depth place it: a short scoped subject sits low, a long, coupled or cross-system one high. Open-ended work (fresh design, ideation) takes each row's top listed effort. A single listed effort on judged work is where that shape usually starts, never a cap. A shape a row's cells do not name: judge it from the row's intel and its nearest named shapes, and a row weaker there takes more effort, not less; never bar it. A `±` limit binds only on the shape its evidence measured.

- **Selection line: you choose which rows meet each job's bar; the fan-out pays among the rows a job lists (rule 2).** Tools drop only rows that are wrong in every case (no tier claim, unavailable, a plan refused on capacity). No listing order or advisory is a pick. The pins a tool fills are an engine's own checked step and a check-scored job's computed effort (`orchestration` §5 *Effort*). Weigh the rest in one pass:
  1. **Fit sets the floor; the job's bar sets how much quality to buy above it.** A row clears the floor when its registry `roles` claim the tier; its `±` cell says how it fares there. The bar is the result the job must deliver: the owner's stated preference for this job when they gave one (a row, an effort, a quality they asked for), else the result its shape and depth need at the balance of cost, time and quality the owner set. Take the cheapest cell that delivers it, in every spend mode. Quality decides where it decides the result (architecting, design, an in-depth defect-hunting review); cost leads where a cheaper cell delivers the same (execution under a settled spec, fan-out including per-item rubric verdicts, extraction, evidence gathering). The lean condition moves the bar to the cheapest cell that does the job reliably (`orchestration` reference `spend_lean.md`). Rigor never moves it: rigor sets how widely and deeply the result is verified, because high stakes buy checking, not a costlier executor (`skills/orchestration/reference/rigor.md`). Where rows match on the shape, a stronger row buys nothing. A board lead inside the judge band is no quality difference.
  2. **Drop first, then pick by rule 1's bar.** A plan `for-role` dropped as exhausted or at its dispatch floor is out: never reconsider it; a plan whose meter cannot be read is unknown, not exhausted, so it stays out of the listing and the launcher's own gate decides. Among the rows `for-role` lists, rule 1's bar picks the rows the job lists, one row or several it cannot separate. Speed buys a faster row that also clears the bar only while the owner or the session's next step waits on the job, because a faster row that costs more buys time nobody uses otherwise; a job nobody waits on, or one under lean, never pays for speed. The fan-out then pays the job: among the listed rows' plans that hold the job in every window (the 5-hour window is a gate, never a rank), one whose weekly or monthly quota is forecast to expire unused at its reset, the earliest reset first, else the one with the most weekly room (its week's quota left against its week's time left), and on that plan the cheapest listed row. A plan ahead of even pace (`provider_bands.ahead_of_pace`: its allowance left falls short of its window left by more than the reading's whole-percent resolution) has no quota unused at reset, whatever its last day's rate, so it never outranks a plan with more room. Quota unused at reset costs nothing; on one plan the `cost` cell compares rows, while two plans' quotas are different currencies. Neither unused quota nor room buys a costlier row: rule 1's bar sets quality. The listing order is the registry's, never a pick. Say quota in the line's own words, naming the window, the share left or used as the line states it, and when it resets; "unused" means only what a forecast says will expire at a reset, never what is left.
- **Review seats:** step 1's floor applies, and a `supplementary` row clears it for an added seat beside a qualified one. Among rows that clear it, prefer a provider other than the subject's author when that provider's plan has room. The preference never adds a seat. For a plan check, set each seat's effort inside its row's review range from the plan's size, coupling and depth. An added opus seat beside a sonnet seat pays on a plan that holds new design decisions, couples systems or runs long (unmeasured).
- **Session vs delegate:** at equal intel the lower-`deleg` row is the better delegate. Pair an orchestrator-row session with architect- and executor-row delegates.
- **A `scout` or `lens` kind** loads less project doctrine than a `reviewer` or `author`, and so cuts first-turn input (`reference/sidecar_dispatch.md` §Job kind). Use `scout` only for locate/enumerate/extract work that applies no project rules.

## Compaction

A pin's compaction point (`model_registry.py usable_window`) bounds a job's whole working set: the subject it keeps resident, its reads and its reasoning. A lane of independent items compacts and carries on. A job that must keep one subject resident (a review seat, a design, a plan, chained research) and outgrows the point can lose the subject at each compaction and cycle: give it a narrower mandate, a smaller subject, or a row whose point holds it. Every Claude dispatch, sidecar or native, compacts at the smallest of its model's window, its row's `compactAtTokens` and the login's `autoCompactWindow` (`model_registry.compaction_point`), so a subject over a row's point needs a row whose point holds it. A Claude sidecar whose point sits below its model's window holds each auto-compaction until it writes its findings to its output file (`hooks/sidecar_recompact_reprompt.py`); on a long audit this cost less than running uncompacted to a larger window, at the same report. A sidecar job that must read a large subject in once and then works only a few turns may set `window: "full"` to skip the login's cap (a row's `compactAtTokens` still applies); every later turn re-sends the whole context, so a job with many turns past the login's point costs more with it. A native agent always takes the login's window. A proxied agent compacts only on an adapter build that detects the client's compaction control.

## Axis definitions

Higher = better on every axis. `?` = no evidence yet.

- **intel:** the hardest problem handled unsupervised.
- **deleg:** orchestration ability (scoping, spec-writing, dispatching, reviewing returns, holding a long plan); it decides who runs a session. `—` = never a session model.
- **taste:** UI/UX, code cleanliness, API design and prose, relative to the owner's preference.
- **speed:** time to completion.
- **cost:** what one result costs at the row's price (registry `price`). On a plan row it weighs quota draw, not money.
- **billing:** vendor · how a call is paid: `plan` spends a subscription quota, `pay-as-you-go` spends money per token, `free` spends neither.
- **effort:** the starting effort per work shape, for `agent()` pins and the session `/effort`. A result at one effort shows it is enough, not that the others fail. An effort the row's registry `effort.avoid` lists is never pinned outside a `sidecar_fanout.py --compare` run or a benchmark campaign file; the guards enforce it. `—` = no effort setting.

Harness load is a third pin beside model and effort: `orchestration` §5 *Per-dispatch harness cost*.
