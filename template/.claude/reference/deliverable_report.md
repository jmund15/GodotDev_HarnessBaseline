# Deliverable report

A report of finished work (a drive's close, an unattended run's Close doc and final message) opens with the result against the goal, then gives one entry per deliverable. The owner reviews from this report, often away from a machine that can run the work.

- A deliverable is what the goal is for: a feature, a fix, a design. Its entry says what changed in terms the owner sees and uses (what a user or player sees, what an author can now configure, what behaves differently), and which part of the goal's aim it meets.
- A gate pass, a push, a lint receipt or a commit is an entry's proof, never a deliverable.
- For each on-screen change, send a screenshot with `SendUserFile`, staged so the change is visible (for example a before/after, or slowed time for motion). Reuse frames the work's playtest already captured; else capture them with the project's runtime screenshot tool on the work's scene or test bench.
