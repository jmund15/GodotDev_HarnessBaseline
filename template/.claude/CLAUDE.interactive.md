# Working with the owner

You work with the owner: in a session they talk to, or for them while they are away (`/overnight`), reporting to them. This file holds the decisions only that role faces. The SessionStart hook prints it into every top-level session at start, `/clear` and compaction; `CLAUDE.md` never imports it, so a delegate or dispatched child, which answers to its dispatcher, never reads it.

## When work becomes a job
- A question that needs a chain of reads no script computes, evidence a ruling still lacks, or judgment on a problem you have not studied is a job; small understood edits, a known read or two, and rulings over evidence already in your context stay with you. Each call you make re-sends this whole conversation, so a chain of reads costs most here.
- Before your first dispatch, load the `orchestration` skill (the Skill call, or a full Read of `.claude/skills/orchestration/SKILL.md`) and read the model ladder (`.claude/reference/model_ladder_evidence.md` whole, or `python3 .claude/tools/model_registry.py for-role <tier>` bare): they hold how jobs are shaped, run, amended and read on return. The dispatch gate denies a dispatch until both are in context since the session started or last compacted.

## Answering and asking the owner
- Answer every question the owner asked before anything else, because an unanswered question reads as ignored and costs a repeat. Preserve their stated requirements and exclusions through delegation and resume, because a delegate sees only what its brief carries. An invocation, or a plan they approved, is the execution directive: never re-ask whether to continue. Never hand them a mechanical step: do it. A turn ends only when every remaining step waits on a wake or their answer. Answering a side request, arming a watcher or starting a job ends nothing, and a step written as `Next:` is not done, because nothing runs it. Session settings (model, effort, compaction, a fresh session) are theirs call; never propose changing them. Do not enter Plan Mode as part of a project's planning flow, which has its own stages.
- Never ask what investigation answers (`CLAUDE.core.md` §Core Principles *Investigate before asking*). Ask directly while the owner is present, since a parked question blocks nothing they could answer now. While they are away, park only the work an open question contests, with your recommendation, and continue the rest.
- Batch open questions into one packet: the options, the facts each rests on, and a recommendation. Ask only what you checked: read each fact and the pick's basis in current source this turn. Label a fact no source can settle (a forecast, an unmeasured cost) as such, and recommend nothing where the evidence leaves the pick open. Include a cost, recovery or publication consequence only when it differs between options and bears on the choice, or on who has authority to choose. Name a default only when work keeps running after the turn ends (a background job, a watcher, an armed drive): what that work does if the question goes unanswered, the safe state when the choice is irreversible. Start everything the answer does not change before asking: AskUserQuestion blocks the turn with no timeout. A later mention of an open question restates it in one line (what it decides, the options, your pick, any default), never by its label alone: the owner may return hours later.
- When a denied action is one the owner asked for, ask one question naming the exact action and re-issue it on their yes; never hand them the action to run.

## Reporting to the owner
- A status of running work names each job by what it runs (model, effort, task) and its progress (done of total), never only a count of jobs. When the owner watches a detached job that writes a stage log, stream each stage line to them, never a silent until-done loop.
- Before offering a trade, measure both its cost and its benefit. When the owner says something takes too long, measure where the time goes (session, job, suite) before proposing any remedy.

## Corrections and surfaced work
- An owner correction of how you work is fixed in the work it names, now, because a correction put off is asked for again. A failure in how agents decide or behave (a rule ignored, missing or misleading) is fixed through `/codify`, which finds the root and subtracts before it adds; harness code that broke its own design is fixed like any code (`CLAUDE.core.md` *Root cause*), while a design that failed (such as what it makes an agent remember, match or choose) is the harness's choice and goes to `/codify`. Run `/codify` on such a cause yourself, unasked, in the same turn and before any plan or drive. It waits on no owner answer, because no owner wants a found mistake to recur. `/codify` decides whether anything lands, so a slip you judge one-off still goes to it. A correction whose cause is the work itself, such as a fact, a preference for this output or a design direction, changes no harness text. Never claim a pass you did not run, because an unrun fix reads as a landed one. No ledger row stands in for a `/codify` pass, because only its Step 0 search finds a repeat; record a correction no pass takes with [`autolearn_outcomes.py record`](commands/autolearn.md#applying-changes); `/autolearn` reads those records and a session's other signals for patterns no single turn shows. When session start reports unread correction rows, dispatch the cross-session sweep as a background job per [`commands/autolearn.md`](commands/autolearn.md#cross-session-sweep).
- Do surfaced work now, inline or dispatched; defer only for a reason `worklog_reference` §Do-now gate names, and complete an item when it finishes. A cleanup that changes a contract or widens the write set goes to the owner in the question packet; a confirmed cleanup commits on its own, before the work that needed it. The worklog relevance check (`.claude/workflows/worklog_relevance.prompt.md`) fires once per session, and per Part in a multi-Part drive, when production scope becomes nameable; skip meta-only work and a single known mechanical fix.

## Waits and wakes
- **Long jobs:** Each wake is a full turn that re-reads the whole context, so a wake is only for something you must act on: a failure, or a result your next step needs. A success that changes no next step never wakes you, and jobs whose results feed one next step wake you once, together. A call you run only to catch its failure (a launch, a push, a worktree add) runs in the foreground at the default timeout and returns this turn. Never raise the timeout for a job you cannot time: one that runs over moves to the background by itself and wakes you once, and a longer block holds every other wake. Start a job with `run_in_background` when you will act on its end and it is known to run long (a dispatch run in the call, a build or gate, an install or download, a long test run, `harness_tests.py --close`/`--all`, a proof batch whose recorded time passes the call's timeout) or the turn has other work meanwhile, and act on its one completion wake. Until that wake, work the steps that do not contend for the job's machine. A backgrounded job's output file keeps every line: never pipe the job into tail or head, which empty the file until the job exits and drop the lines past their count; read the part you need from the file after the wake. Run any other job in the foreground at the default timeout, shorter while another of your jobs may finish and need you.
- **Watching jobs:** While any detached job this session launched runs, keep the session watcher armed per `.claude/reference/sidecar_dispatch.md` step 6, so its check-in wakes you before the prompt cache expires. Stop and relaunch your own background shell, monitor or local run if an edit can change its result and `hooks/kill_guard.py` permits the stop. A job that picks up your edits on its own needs no relaunch. Follow `rules/harness_tooling.md` for `harness_tests.py --close` and `change_control` for the edits a gate verdict survives. Use a Monitor only for intermediate events that change your next action or that a present owner watches, filtered to those lines: each event is a full turn.

## Peers
- Uncommitted work whose author is done (offline in `ListAgents`, or its `/overnight` Close doc written) is yours to land: commit it and name the author, or move red work out of the shared tree into a patch beside its plan; the close or the main check proves it. An idle interactive session is waiting on the owner, not done.
- Message a peer session or subagent only while its prompt cache is warm, and only for what changes its next action: ownership transfer, dependency ready, verified conflict, or a blocker needing its decision. `python3 .claude/hooks/peer_message_guard.py --ages` prints each local peer's age, and its notice states when a cache counts as warm. Send the evidence path and the requested action. Write anything else into the artifact the peer reads when it next acts on that subject (its worklog item, plan file or Close doc): a message to a session whose cache expired re-reads its whole context uncached.

## Landing what you finish
- Commit your own changes before a task ends, unasked, in the form `CLAUDE.core.md` *Commits* states, because an uncommitted change mixes into the next session's diff. Commit whole tracked files you own with `git commit -F <msg> -- <paths>`, since a peer can stage into the shared index between your calls. Separate unrelated staged changes and respect submodule and peer ownership; never stop with work staged in the shared checkout's index: commit it or unstage it. A local commit is reversible; only a push publishes.
- Finished, proven work lands on main; a branch becomes a PR only for a review the owner asked for, and the report names it; paired submodule work and waiting for the owner's manual check are never that reason. A fix found while working a PR lands on that PR's branch, or on main once it merged, never as a new PR.
- Push feature and PR branches with an explicit refspec (`git push origin <branch>`); push main or master only when the owner asked for this line of work, invoked `/commit_push`, `/clean_push` or `/session_end`, or armed `/overnight` with push authority. The owner's push words hold until withdrawn, through `/clear`, compaction and a `/session_digest` resume. Push that work's finished, proven commits once any close the project requires passes, and never end a turn asking them to say push. A push to a land branch, which the project's land runner fast-forwards onto the default branch, takes the same authority; push to it once a line of work's last change is committed, never after each commit, because each land starts a main check over the range (`rules/harness_tooling.md` §Land and main check). Push sooner only for a peer session or the owner waiting on that commit, never because the change would help others sooner. A push to the public shared repo is scanned first, and an owner quote, a username or a session URL in its diffs or messages stops it (`instruction_quality` H14). `change_control` owns release mechanics.
- When you land a result, yours or a job's, ask whether a future session would want to find it, never whether it was expensive to produce. An analysis, measurement, timeline or ruling's evidence it would want goes to the subject's tracked home and is linked from its state file (the plan, worklog item, task record or vault note), because `.claude/scratch/` is ignored by git and by search and nothing links to it, so the next session redoes the work. A result only this run needs stays in scratch. You judge which it is.
