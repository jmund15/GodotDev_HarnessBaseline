## A Note from the Owner
I don't want systems convoluted or difficult to navigate, quite the opposite. I like ambitious ideas, but simple systems, and software that feels obvious. Do not preserve unneeded complexity just because it exists. Understand the real constraint, then fight for the smallest model that makes the correct behavior unsurprising. Channel "measure twice, cut once" - this is a LARGE, expansive codebase with many systems that interact with each other. However they are all and should all be built with extensibility, reusability, and interoperability in mind. This means when adding a new surface or feature, you may be able to find components or subsystems that have already done the work for you. In the case of large new feature integrations or refactors, the goal is emergence and reactive, not hard-coded.

Finally, one of the most important aspects of our work together — communication. Every word we say together reinforces our clear, concise, actionable communication. I read the last thing you write first, and much of what you write is read later — by me after a run, or by a delegate with none of this context — so the answer opens, the next action closes, and the close stands alone. Use plain, specific language. State each fact once, do not repeat yourself in the same prompt. Optimize for clarity and engineering value, not quotability.

Our main goal is to streamline communication and maximize efficiency. So in larger-scope sessions, use **Reference Points**:

Use numbered lists and markdown headings when they improve navigation.
When presenting three or more findings, decisions, options, risks, questions, or actions assign every one a short code.
Use D1, D2, DN for decisions.
Use O1, ... for options.
Use F1, ... for findings.
Use R1, ... for risks.
Use Q1, ... for questions.
Use A1, ... for actions.
Invent new references for sections we don't have.
Preserve the same codes throughout the conversation.
Do not create codes for short simple answers.

## Core Principles
- The harness's goal is accepted results at the least time and cost, quality held fixed; quality is how cost falls, since rework costs most. A step, review round, guard, rule or widened scope earns its place by what it catches against what it costs, measured where a measure exists, and steps that stop paying as models improve are removed; when rules pull apart, this decides.
- Identify the domain and retrieve relevant evidence before acting. Verify decisive premises, not just their citations.
- Keep scope and quality intact. Missing, failed and unverified are not clean; report actual tests and artifacts.
- A result outside its expected value is a defect, never a finding to report: trace it to its cause in the primary evidence first, then fix it, or name the blocking fact, in the same message. This covers a measurement the user ordered as much as a failing test. Trace past an outside mechanism (client, provider, OS) to the first link the harness owns; a blocking fact has no owned link upstream of it. When a mechanism the harness owns (a check, guard, test, default, flag, launcher or workflow) blocks or slows correct work, that mechanism is the defect: fix it at its owner before any workaround (`rules/harness_tooling.md` §A guard that blocks justified work is a guard defect).
- Check current git state and preserve peer work. Run `git status --short <file>` before calling a defect peer-owned; clean means it is yours to fix now. Uncommitted work whose author is done (offline in `ListAgents`, or its `/overnight` Close doc written) is yours to land: commit it and name the author, or move red work out of the shared tree into a patch beside its plan; the close gate proves it before push. An idle interactive session is waiting on the owner, not done. A local commit is reversible; only a push publishes.
- Message a peer session or subagent only while its prompt cache is warm, and only for what changes its next action: ownership transfer, dependency ready, verified conflict, or a blocker needing its decision. Warm means `ListAgents` shows it `busy`, or its last turn ended under 50 minutes ago for a session (an idle one compacts near 54) or under 4.5 minutes ago for a subagent (5m cache). `python3 .claude/hooks/peer_message_guard.py --ages` prints each local peer's age. Send the evidence path and the requested action. Write anything else into the artifact the peer reads when it next acts on that subject (its worklog item, plan file or Close doc): a message to a session whose cache expired re-reads its whole context uncached.
- Thin evidence informs a decision; it never makes one alone. Reason out what the mechanism predicts before treating one or two cases as a rule: one case can refute a general claim, never establish one. Where reasoning and evidence disagree, find out why before acting, and name what would reverse the decision. A rule marked `basis: thin` or `basis: reasoned` binds like any other; record what contradicts it, and never cite it as settled.
- One rule, one owner: every other surface cites it, and a reader loads only the unit its decision needs (`instruction_quality` §3, §5). A fix or design for one surface names the class it belongs to and covers every member and every caller, or names why one is excluded (`auto-memory/feedback_fix_the_class_not_the_instance.md`), with the smallest change that removes their shared cause: correct or delete what produced the failure before adding a rule, tool, guard or stage.
- A dispatch that returns findings, claims or verdicts arrives verified and folds the findings it can act on: the run checks them and the result carries the verdicts (`orchestration` §8). Only a VERIFIED claim is accepted unread; read the source of every UNVERIFIED or UNCHECKED claim before acting on it (`commands/agents/orchestrator_action_protocol.md` Step 1.5), and rule only `held` ids and failed checks.

## Developer Tooling Strategy

### 2. Memory (One Store, Two Tiers)
Canonical bodies live in `.claude/auto-memory/`; this overrides the runtime's default `~/.claude/projects/<project>/memory/` store, which holds only one-line pointers. `MEMORY.md` is the loaded index; cold material remains searchable, normally under `archive/`. Search by concept with `mcp__plugin_semantic-search_semantic-search__search` and a repo-relative POSIX `restrictToDir`; use literal search for exact values.

Default new learning to cold. Hot admission requires a decision most sessions face before any trigger/search could deliver it, not spare space or an interesting incident. Add a hot pointer in the same turn as its file; stay below the runtime's 200-line/25KB cap. Move a file-class rule to its triggered owner while retaining its evidence. `/codify` owns placement details. Save surprising constraints/preferences, not API inventories, code descriptions or facts recoverable from git.

### 4. WebFetch (The Documentation)
Verify version-sensitive facts against `reference/project_stack.md` and first-party sources. `reference/source_trust.md` §Fetch order owns the order.

### 5–6. Git
Commit your own changes yourself before a task ends, unasked, in categorical commits (feat/fix/refactor/chore, one logical concern each, path-scoped): an uncommitted change mixes into the next session's diff. Finished, proven work lands on main; a branch becomes a PR only for a review the owner asked for, and the report names it; paired submodule work and waiting for the owner's manual check are never that reason. A fix found while working a PR lands on that PR's branch, or on main once it merged, never as a new PR. Push feature and PR branches with an explicit refspec (`git push origin <branch>`); push main or master only when the user asked for this line of work, invoked `/commit_push`, `/clean_push` or `/session_end`, or armed `/overnight` with push authority. The owner's push words hold until withdrawn, through /clear, compaction and a `/session_digest` resume. Push that work's finished, proven commits once the close passes, and never end a turn asking the owner to say push. A push to a land branch, which the project's land runner fast-forwards onto the default branch, takes the same authority. Separate unrelated staged changes and respect submodule/peer ownership; never stop with work staged in the shared checkout's index: commit it or unstage it. `change_control` owns release mechanics. A decision doctrine commit carries a `premises` block when it rests on a claim (`reference/evidence_contract.md`). A push report names each decision commit no review covers.

### 9. Tool Routing — Pre-Call Litmus
- **Known, focused evidence or line-level judgment:** Read the needed source. Do not force a small audit/debug read through a lossy summary because of its path or a read counter. Decide at a question's first call: one that needs a chain of reads (a scan, an extraction, log or transcript digging, a status trail) goes to one script that prints the answer when a script can compute it, else to the route `orchestration` §0 picks. A read chain costs most in the main session: each call re-sends this whole conversation, and each result stays in it for every later turn.
- **Large exact scans/counts/joins:** use deterministic extraction with bounded output. Scan the complete intended source; report missing/unparseable inputs separately.
- **Copyable bulk I/O:** use the configured ai-worker MCP when its input fits. Check the local queue before a local call; require complete per-input results. A failed or degenerate return is incomplete, not evidence.
- **Search/fetch and every shell read:** bound the walk, and print only what the next decision consumes: a tool's usage block or listing, not its docstring; the needed fields, not the whole record. Use git-aware tools (`git grep`, the Grep tool, `rg --max-count`), or `rg -uu` inside a gitignored tree such as scratch; recursive grep walks are denied. Follow the source-fetch owner above. Use only tools present in the live schema.
- **Writing:** `.claude/` harness files (instructions, hooks, settings) use direct Edit/Write, never a shell write, which skips their edit gate. Judgment-dense docs use direct writing; templated/mechanical prose uses `write_doc`. Name the doc class, preserve structured/Mermaid blocks, and verify the artifact. Micro edits use Edit.
- Recover existing output before another dispatch.
- **Offline fallback:** when the worker or semantic search is absent, bounded `Read` (`offset`/`limit`) is the floor. Never loop on a nudge toward an absent tool.
- Load deferred tool schemas in one batched `ToolSearch` call; each loaded schema stays in context. Disk edits do not evict loaded text or prove cache invalidation.

### 10. Harness Baseline (Shared Config)
`baseline.lock.json` identifies shared ownership; `/sync_baseline` owns classification, drift, pull/fork and publication. Keep project-specific changes local. A commit guard requires a lock row for each new `.claude/` file; `--check-baseline` adds the drift check before push. Never publish another session's unreviewed changes.

## Core Code Conventions
Follow the authoring tool: snake_case for Python tooling; match neighbors for Markdown/images. Comments default to none: add one only where deleting it would lead a maintainer to a wrong decision. Prefer clear contracts and authored data over special cases.

## Shell Discipline
- **Bash calls:** Use `git -C <path>`; Bash cwd persists. Write Python carrying nested quotes, or backslashes inside a `claude -p` child, to a file. Python file writes use LF (`newline="\n"` or bytes). Quote paths. Commit messages go in a file under `.claude/scratch/` (gitignored) for `git commit -F`, not `/tmp`. Tracked `add && commit` calls fold to pathspec commits before guards. Run every other fix or prep step, index writes (`add`, `rm`, `reset`, `stash`) included, in its own Bash call before the guard-gated call. Guards read the index before the command runs, and a denied compound runs none of its parts.
- **Destructive operations:** Name each target in the question or reply by the name its tool binds (a process by pid and launch label), never a pointer to a list. Get the owner's words before `git reset --hard`, `clean -f`, a checkout or restore that discards edits outside your own worktrees, force-push, `branch -D` of unapplied branches outside `scratch/*`, unpreserved `stash drop` or `stash clear`, `reflog expire`, `gc --prune`, `filter-*`, a recursive delete outside caches, temp dirs, clean scratch clones, your own worktrees and orphaned worktree directories holding only files git has and regenerable caches, drive formatting, or `TaskStop` on a dispatched agent or workflow. Ownership means this session provably created the worktree; only then may its ignored files go with it. Recursive worktree deletion also requires clean, pushed retirement (submodules included) and no other live session working in it. A guard denies only a loss it observes and reads no reply; the auto-mode classifier judges whether the owner asked.
- **Long jobs:** In a session that receives completion wakes, each wake is a full turn that re-reads the whole context. Start a job with `run_in_background` when it is known to run long (a dispatch, a build or gate, an install or download, a long test run, `harness_tests.py --close`/`--all`, a proof batch whose recorded time passes the call's timeout) or the turn has other work to do meanwhile, and act on its one completion wake. A backgrounded job's output file keeps every line: never pipe the job into tail or head, which empty the file until the job exits and drop the lines past their count; read the part you need from the file after the wake. Run any other job in the foreground at the default timeout, shorter while another of your jobs may finish and need you. Never raise the timeout for a job you cannot time: a job that ends in time returns this turn with no wake, a job that runs over moves to the background by itself and wakes you once, and a longer block holds every other wake.
- **Watching jobs:** While any detached job this session launched runs, keep the session watcher armed per `reference/sidecar_dispatch.md` step 6, so its check-in wakes you before the prompt cache expires. Never re-run a status check call after call. Stop and relaunch your own background shell, monitor or local run if an edit can change its result and `hooks/kill_guard.py` permits the stop. A job that picks up your edits on its own needs no relaunch. Follow `rules/harness_tooling.md` for `harness_tests.py --close` and `change_control` for the edits a gate verdict survives. Use a Monitor only for intermediate events that change your next action or that a present user watches, filtered to those lines: each event is a full turn.
- **Processes and permissions:** Stop an OS process only through `python3 .claude/tools/reap.py` (usage in its docstring); never kill a peer from a path substring or idle label. Ask the owner to close terminal windows; never close one by title or host process. A rejected permission/config operation stops that operation; do not change permission mode or route the action through another tool to get around it. When the owner watches a detached job that writes a stage log, stream each stage line to them, never a silent until-done loop.

## Preferences
- **Working:** Preserve stated requirements and exclusions through delegation and resume. No performative agreement: check an objection against the evidence, then fix it or dispute it with that evidence. Distress language means stop and rescope. Never hand the owner a mechanical step: do it.
- **Reporting:** Keep full evidence retrievable while returning only the current decision, result and next action. A status of running work names each job by what it runs (model, effort, task) and its progress (done of total), never only a count of jobs. A bullet headline states the actual point, never a category label.
- **Asking the owner:** Batch open questions into one packet: the options, the facts each rests on, and a recommendation. Ask only what you checked: read each fact and the pick's basis in current source this turn. A delegate's draft returns its facts in a claims fence. Label a fact no source can settle (a forecast, an unmeasured cost) as such, and recommend nothing where the evidence leaves the pick open. Include a cost, recovery or publication consequence only when it differs between options and bears on the choice, or on who has authority to choose. Name a default only when work keeps running after the turn ends (a background job, a watcher, an armed drive): what that work does if the question goes unanswered, the safe state when the choice is irreversible. Start everything the answer does not change before asking: AskUserQuestion blocks the turn with no timeout. A later mention of an open question restates it in one line (what it decides, the options, your pick, any default), never by its label alone: the owner may return hours later.
