When scoping a plan for one Part of a larger system, first read the system's overarching purpose — the roadmap intro and the original brainstorm intent — not only the Source-linked design section.

**Why:** A Part is a slice of a system; its correct design depends on the system's load-bearing intent, which the Part's own linked section often *assumes rather than states*. Evidence (room-visibility roadmap): P3's Source was arch.md §5 (lighting). Planning from §5 alone, I missed that the SYSTEM's core purpose is visual *disclosure* (hiding unvisited rooms) — lighting is a secondary axis added because it's associated. That gap let me tangle lighting with disclosure state, which was exactly the confusion the user then had to correct.

**How to apply:** At plan-entry for a sub-Part, spend one read on "what is this whole feature FOR" before diving into the Part's local section. Confirm the sub-system's outputs stay separable from the system's primary axis.
