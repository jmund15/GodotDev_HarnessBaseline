Dynamic Workflow `parallel()`/`pipeline()` fan-out runs N subagents concurrently (cap `min(16, cores-2)`, overflow queued). Two {{PROJECT_NAME}} resources are SINGLE-FLIGHT and will wedge if multiple concurrent agents touch them:

- **GdUnit4 test runs** — one test run per checkout at a time (the checkout lock), and the machine's runtime slots are few; the sole exception is the gate's own run pool, which runs its Logic/Integration/retry children concurrently inside the one checkout hold it already took for its build, so it is not a second agent racing the lock. N agents each shelling `dotnet test` / invoking the regression gate either queue on the checkout lock or time out on `LOCK_TIMEOUT` once the slots are full, and bare `dotnet test` bypasses both and wedges the pipe with orphans (the ~2h-loss crash class in `GdUnit4_Process_Management`). A worktree-isolated lane escapes the checkout lock but still needs a free runtime slot and pays its own import and build, so concurrent runtime-test lanes stay within the slot count (`orchestration` §2 Width). Each run under a `-ResultsRoot` tag (the gate's held children included) is isolated per run: its own pipe suffix (`<worktreeId>-<Get-RunTag>`), APPDATA, TRX and Godot log, so a gate's own concurrent children do not cross-talk. Test EXECUTION must serialize: run the gate ONCE, serially, in the orchestrator (Claude) OUTSIDE any `parallel()` barrier — never inside a fanned agent. Investigation and fix-authorship may fan out; shared-checkout fanned agents run no tests, and worktree lanes run scoped tests only within the slot count.
- **csharp-ls LSP wrapper** — single-flight (`CSharp_LSP_Runtime_Gotchas`); concurrent `findReferences`/`documentSymbol` wedge it until a full Claude Code restart. Pre-compute the symbol map ONCE orchestrator-side BEFORE the fan-out and pass results into agents as CONTEXT/args. Forbid LSP in fanned agent prompts; instruct Grep/Read only.

DISTINCT from the existing "LSP unavailable on cloud" carve-out (that is availability; this is single-flight-under-concurrency). The latent trap surfaced in the harness-workflow audit: a per-PR review fan-out where each agent runs the project's PR-review command, whose test phase invokes the regression gate → N concurrent gates. Bake "read-only, do NOT run the regression gate" into the fanned agent prompt; the gate runs once above the barrier.

**Guard reaches only the top-level fanned agent — nested fan-out escapes it.** The `review_fanout.js` `BASE_CONTRACT` (its CONCURRENT line forbids single-flight tools) is text *appended to the dispatched agent's prompt*. If that agent itself spawns sub-agents (e.g. each per-PR agent running a PR-review command that spawns 4–7 sub-agents), those sub-sub-agents receive their OWN prompts without the contract — so "no regression gate, no language server" silently lapses one level down. Rule: do NOT route a *nested* fan-out command through the generic engine; keep it Claude-orchestrated. Also: the engine treats location as an anchor, never identity, and does not dedup by `file:line`, so same-location hits stay separate findings; a cross-PR conflict still needs a bespoke or keep-as-is shape to be recognized as one.

Workflow scripts also have NO filesystem access — file reads happen inside agents or via `args`. See [[workflow-integration-mechanics]].
