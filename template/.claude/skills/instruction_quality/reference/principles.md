## Harness principles

Every change to agent-facing harness text meets these, and every review of one checks it against them by number. Agent-facing text is whatever an agent reads to decide: the `CLAUDE.md` chain, `CLAUDE.interactive.md`, commands, skills, references, rules, rails, lens files, memory, and any string an agent reads inside a hook or tool (a deny, injected context, tool output it acts on). Harness code is built like any other code: it meets H4 through `CLAUDE.core.md` *Build on what exists*, H5, H8, H9, H13 and H14 through `rules/harness_tooling.md`, and plan check and diff review weigh its removals under H2. The owner's words behind each principle are filed under its number in the project's harness goal file, kept in its `.claude/` folder when it has one; read it with this file when it exists, and reread a principle's words whenever its reach is in question.

- **H1. The owner's words set the goal; a measure an agent made is a labeled proxy.** A number, cap, list, count or gate the owner did not set may be proposed, labeled as a proxy, and decides a cut, a round or a done-claim only on the owner's yes, because a proxy that decides passes while its purpose fails, and the harness then enforces it on every later agent. Litmus: delete the number; does the rule still say what to do?
- **H2. A piece stays while it serves the owner's work more than it costs.** Read its value from why it was built (origin commit, the owner's words): a function the owner uses, a loss it prevents, a decision it makes better or cheaper. Usage, size and fix count are considerations, never the verdict. Adding and cutting both take the weighing, because counting only catches grew the harness by patches and counting only size gutted it. Mechanisms take `reference/mechanism_litmus.md`. Litmus: can you name what it does for the owner, from its origin, and what it costs in time, tokens and friction?
- **H3. Fix at the root, and subtract before adding.** Name the way of thinking that failed before the file that failed; correct or delete the cause before adding anything; a repeat names why the last fix of the same decision did not hold, and that answer picks the fix (§3b). Every fix to a failure in how agents decide or behave runs `/codify`, because a fix written outside it layers a patch where the root belongs; harness code that broke its own design is fixed as code, and a design that failed (such as what it makes an agent remember, match or choose) runs `/codify`. Litmus: what does this change remove, and why did the last fix not hold?
- **H4. Read history before changing or removing.** Read a line's origin commit, its fix history and any plan or vault design its commits cite (`git log --follow -S`) before changing it, because why a piece exists lives in its history, not its text. Litmus: can you say why this line was written?
- **H5. Judgment stays with the agent; a tool computes only what observed facts settle** (§3's sort). A tool, table or gate never refuses a choice that needs judgment, such as a drive's sizing, a job's model and effort within its role, or whether another review round is owed; it prints the facts. A tool may refuse on an observed fact: a role's admission, a path, or an absent grant. The grant itself is the dispatcher's judgment, carried in the job's own field. Reading what the owner means is the model's job in the same way: a rule that turns the owner's words, or any other judgment, into a condition-to-action table is itself judged against this principle, and a general principle that helps stays. Where a new rule about reading intent seems needed, state the principle and name what the agent is trusted to judge, because a table fixes the case that failed and breaks the next. Litmus: could two correct agents, given the same facts, act differently because of something the tool cannot read?
- **H6. Each piece of harness text reaches exactly the readers who face its decision, when they face it, and no one else** (§5's layer table). Place it in the narrowest layer whose readers all face its decision before a narrower trigger could deliver it. An active rule never lives in memory, and procedure a trigger can deliver goes to that trigger's owner. A rule every agent reads but one role uses distracts the rest and can contradict their own rules, and a rule loaded after its decision is never applied. Which projects receive a file is a separate axis (the baseline layers: pure, coding, godot, project), and a file split on that axis loads like its parent. Litmus: who meets this decision, and when?
- **H7. Every rule carries its reason where the agent meets it**: one clause naming the cost it prevents, so an agent can tell a case it does not cover. Rules stripped to their verdict were ignored or applied past their reach. Litmus: could an agent holding only this line tell when it does not apply?
- **H8. Friction only where the agent broke a rule it already held.** Every deny or ask names a rule that was in the agent's context before the call (§3), because a deny that teaches a rule the agent never held blames it for a gap in the text. Litmus: would the agent reading this deny think "I knew that"?
- **H9. What is deterministic is the tool's; the agent sees purpose and call shape.** A tool computes and applies what facts settle (an engine default, a route, a spill path), and an agent meets a mechanism only when it changes it: a table is read at its use, its ingest tool at its edit, because a mechanism the agent must understand to run adds reading and no decision. Litmus: does the agent need this to decide, or only the tool to run?
- **H10. Process sizes to the work.** A drive, review round or close states its sizing by judgment from the work's reach, how settled its design is, and the rigor in force, with derived facts printed beside it; no table or count admits or refuses a stage, and a later round reaches only what materially changed, because a fixed pipeline wastes the owner's time on a one-line fix and thins a change that reaches far. Litmus: which fact about this work sets this stage?
- **H11. Cost, time and quality balance through the owner's dials.** `normal` is the owner's balance of cost, time and quality. Rigor sets how widely and deeply results are verified. The job's bar and the lean condition set which cells jobs run on (`orchestration` references `rigor.md` and `spend_lean.md`; the ladder's rule 1). A harness change never fixes that balance as a pinned model, effort, count or cap. Litmus: does this change pick something the dials and the ladder should pick per job?
- **H12. Work done twice becomes a helper.** An analysis the harness has run before runs through a helper at the tool that owns its subject, with its method stated; a session looks for one before starting, because a repeated analysis costs the same each time and drifts between runs. A finished analysis a future session would want stays where it can be found (tracked, and linked from its subject's state file), because a result left in gitignored scratch is found by no one and gets redone. Litmus: will a later session redo this?
- **H13. A test asserts a decision, never wording**, and lands only where the mechanism litmus holds; a slow suite is fixed at its cause, never trimmed to a number (`rules/harness_tooling.md`). Litmus: can a valid edit turn this test red?
- **H14. Shared text serves every consumer and stays private.** A shared rule names no project's checks, and a project rule may add to a shared one, never weaken it. An owner quote, a username or a session URL never enters the public shared repo, its commits included; the pre-push scan stops a push carrying one. Change a shared file upstream through `/sync_baseline`, never by a local fork; `/sync_baseline` owns classification, drift and publication. A shared file reaches every consumer and the public repo, so a private word in it cannot be taken back. Litmus: would this read correctly in the other project, in public?
- **H15. Harness text reads clearly to both its readers, the owner and the agent.** Plain words, the action first, one idea per sentence, names that say what a thing does, and a structure a newcomer can navigate. Succinct, never at the cost of a needed reason or case. Text the agent half-reads is applied wrongly, and text the owner cannot read cannot be corrected. §6 and §6b are the method. Litmus: could the owner and a fresh agent each act on this line after one read?

## Layers

Every rule sits in the layer of the agents that face its decision (H6). A line belongs to the narrowest layer whose readers all face its decision before a narrower trigger could deliver it.

| Layer | Who reads it | Home | Admits |
|---|---|---|---|
| Every agent (universal) | every session and every delegate, and every child launched in a project checkout | the project `CLAUDE.md` with every file it imports (the shared `CLAUDE.core.md` and the layer files): they are split by baseline layer, not by moment | the owner's notes; principles any agent here applies, each with its reason; the floor's rules; project facts every reader needs. Test: would a correctly briefed delegate, on any job here, decide differently without it? |
| Interactive | a session the owner works with directly, an `/overnight` run that reports to them, and a top-level headless run on their behalf; never a dispatched child | `CLAUDE.interactive.md`, printed by the SessionStart hook at every start, clear and compaction | when work becomes a job, answering, asking and reporting to the owner, their corrections and surfaced work, its own waits and wakes, peers, landing and pushing, where a finished result stays |
| A dispatch | a session that dispatches, from its first dispatch | the `orchestration` skill, whose body the client re-attaches after a compaction, and the model ladder (the dispatch gate) | job shape (gather and judge, who designs), briefs, width, model and effort, amending or stopping a running job, reading and verifying returned work |
| A drive | the session running one | the entry command and its drive stage files; the task record | stages, sizing, halts, the record, close |
| A delegate | each job | `guards/common.md`, its kind file and project overlays, then its brief | return, write set, claim rungs, waits without wakes, kind duties |
| Changing the harness | whoever changes agent-facing harness text | this skill, `reference/principles.md`, the project's harness goal file where it has one, `reference/mechanism_litmus.md`, `/codify` | the harness principles and these writing rules |
| Harness code | whoever changes it | `rules/harness_tooling.md` by path, plan check and diff review | code rules and the principles the opening paragraph names for harness code; strings an agent reads (a deny, injected hook context, tool output an agent acts on) are agent-facing text under §3 and §6 |
| A step | whoever runs it | the command, skill section, reference or tool that owns the step | procedure |

A rule another layer states is cited, never restated. A child in a project checkout receives the every-agent layer natively or from its launcher; a `scout` or `lens` child runs where it loads none, by design, and no rail restates it. Count loaded bytes per reader, references included. A byte count is a readout: the loaded-set caps live only in `load_census.py` `BUDGETS` (§5 A5), and the one limit the harness does not set is a client's, such as the hook-text cap a SessionStart part carries or a skill's re-attach cap. `MEMORY.md` reaches every agent and indexes recall hooks: a topic and the file that holds its rule. A rule every session faces before any trigger lives in the layer that reads it, never only in a hook.

For a triggered body, a rule unit states one decision, its trigger and one non-obvious clause; the rest is evidence for cold storage. Split a body when a typical invocation needs less than half of it: move the detail layers into `skills/<name>/reference/*.md`, and cite each from the step that reads it. Preserve required obligations and reachability, not the original rule count. Every decision addition receives the focused audit, and an addition that adds a new decision rather than sharpening an existing one records its reason. Remove only redundant, stale, duplicated, narrative, unreachable, obvious-negation, friction or overfit text (§6), never a load-bearing rule to balance bytes. A body past `load_census`'s oversized threshold is a review trigger, never a cap: the close's hot-set review applies the split test above, a split keeps the complete rule with its evidence, and no edit trims text to meet a byte count. The CLAUDE.md byte band does not apply to skills; they are not always-loaded.

## Doctrine commits

A decision doctrine commit carries a `premises` block when it rests on a claim (`reference/evidence_contract.md`). A rule marked `basis: thin` or `basis: reasoned` binds like any other: record what contradicts it, and never cite it as settled.
