# Integration: a running or returned dispatch

## While a job runs

A running author job is amended by writing `<its brief's full file name>.amend.md` beside the brief (`S.md.amend.md` for `S.md`): new owner words or a wrong brief then cost no relaunch and no owner question, and a paid job is never stopped to give it input. Words written before the job launched are not delivered, so they go into the brief; one job of a brief that several jobs share takes `<brief>.<label>.amend.md`, which reaches only that label. `hooks/amend_delivery.py` delivers the full text to the job at its next tool call, again whenever the file changes, and blocks the job's stop on a revision it never received; the job reads nothing unless the amendment passes the client's 10,000-character hook-text cap, and then only the rest the delivery names. A message may resume a finished agent; do not reopen a completed audit or review files still being edited. Never edit a running fold's subject or writer's write set: wait for its result, or use a worktree.

A run that has spent tokens stops only on an observed fact of waste: a finished result about to be re-paid, an orphaned, stalled or duplicate job, a balance below its floor, a spent allowance, or a provider's usage-limit rejection. A cost estimate never stops one, because it measures a run's size and so stops the largest legitimate run first. Never stop a paid job to give it new input or a corrected brief: amend it, so what it spent is kept. Whatever stops a run leaves it resumable.

## When it returns

A dispatch that returns findings, claims or verdicts arrives verified and folds the findings it can act on: the run checks them, and the result carries the verdicts. Only a VERIFIED claim is accepted unread; read the source of every UNVERIFIED or UNCHECKED claim before acting on it (`commands/agents/orchestrator_action_protocol.md` Step 1.5), and rule only `held` ids and failed checks.

**Reading a design or answer.** Before a design or answer goes to the owner or to an author, whether a job wrote it or a drive stage you ran did, read it with what you know and answer three questions. 1. Does it hold to the owner's words on the subject, for every case their reason covers and not only their examples, and to the standing design it changes (the owner's recorded intent, the plan, the text it rewrites)? Judge its scope against the owner's principle, never against the brief that asked for it: the brief may be where the scope narrowed. 2. Does it hold where it runs: under the load, timing, concurrency, input size and state it will meet, not only in the case in front of you? 3. Is its owner-facing text plain? Agreement is not a read. Then take the step that first gets whatever would change what the next step spends, and say why. You classify the return from what you read; these are the usual states, and a return that fits none is yours to judge: the owner decides first when an open fork's answer would change the design (direction, the scope the owner set, taste or appetite) or the design departs from the owner's words, since a check run before the answer reviews an assumption: send the summary, its forks and a recommendation for each, and investigate whatever a read or a run can settle, because being unsure is not a fork. A check comes first when the owner's words settle the direction, correctness is what is uncertain, and a miss costs more once executed. Both run at once when the forks are local, so the check's findings stand whichever answer comes. Go straight on when the direction is settled and the next stage shows a miss cheaply. Send it back when the result misses what its stage owed (in a drive, its Complete-when line): a missing fact goes to a targeted gather, and a design gap goes back to the design with the gap named.

`dispatch.js` checks declared returns and recognized claims/findings fences against `reference/evidence_contract.md` and returns a `verification` block with applied verdicts. A job declaring `fold: {findings, digest, snapshot}` or `ledger: {stage, subject, roster, scopeJson}` selects its review closure. The parent checks each required standalone findings/claims deliverable's schema and completeness and runs its applicable `tools/post_check.py` route when no checked block was produced. In review mode the report carries fold results, held items, failures and ledger rows; the parent rules these per `commands/agents/orchestrator_action_protocol.md` Step 1.5. Preserve original findings and provenance on integration (Step 1 there owns location versus defect identity). The Stop audit recomputes checked verdicts and blocks on a mismatch or an unapplied verdict.

A writer's change is judged as a review before you accept or report it (`CLAUDE.core.md` §Core Principles). Read its whole diff, tests included, against the rules its changed files fall under: each `rules/*.md` whose `paths:` match them, read now, because a diff read through Bash loads none of them. Judge it also against the class its fix must cover (every caller and route its rule reaches) and against the obvious design the owner's note asks for. The report's account of its own runs is a claim: restate a RED, a pass or a cost only from the run line it cites.

Compare intent with what ran. Before dispatch, write the announced job list (label, model, effort, transport, role per job) as the manifest seed; after the run, build the manifest (`orchestration_metrics.py --manifest-seed`). Record each `drift` entry and each label the manifest refuses in that job's rating note. A missing label, or a brief mandate with no returned seat, is UNCOVERED (`orchestration` §2's coverage rule).

Recover before another paid call (artifact, then transcript or `/salvage_fanout`), and confirm a job is terminal before replacing it. Rate each result on consumption (`/orchestration_metrics` §Incremental rating).
