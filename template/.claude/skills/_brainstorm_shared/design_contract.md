# The Design Contract — invariants for autonomous architecture work

> Single source of truth for WHAT must hold when an agent runs a design process autonomously. [`/design_drive`](../../commands/design_drive.md) is the consumer; future autonomous design surfaces reference this file rather than restating it.
>
> **Scope split — verification, not cognition.** This file prescribes artifacts and gates (what must be true at design-lock). It deliberately does NOT prescribe process (what to read, what agents to spawn, exploration order or depth) — that is the orchestrator's judgment per the `orchestration` skill. Every clause here exists because the agent *can't know* project facts, *doesn't own* taste, or is *structurally biased* about its own designs — never because it can't structure its own thinking. Apply that litmus before adding a clause.

## Clauses

The design-lock report (clause 8) states, per clause, how it was satisfied — or what couldn't be.

1. **Grounding** — every design decision cites its source: the house design doctrine (`architecture_philosophy`, plus the project's framework skill and `project_subsystems` when the topic touches them), the project's design-direction source, an existing design doc, the roadmap, auto-memory, the codebase inventory, or a user-stated prior. A question no source answers is, by definition, a taste-fork (clause 2). *Litmus: "can I cite where this answer comes from?" No → taste-fork, never a guess.*
   - Cite docs for authored design intent and their own contracts; check claims about shipped behavior in code and its consumers before relying on them. A doc comment alone does not establish that a runtime seam is live.
   - Load the doctrine before drafting; revisit its relevant rule when new design elements or a conflicting premise arise.
2. **Taste is never decided** — [`appetite_invariant.md`](appetite_invariant.md) governs classification. Taste-forks accumulate into a batch for design-lock; a taste-fork the design cannot proceed past is a halt, not a judgment call. N batched taste-forks at design-lock is a SUCCESS state (`appetite_invariant.md` §Why this is load-bearing).
   - **The batch persists as it accumulates:** each fork is appended to `decisions.md` `## Frontier` as it is classified, per [`flow_and_frontier.md`](flow_and_frontier.md) §8.
3. **Independent adversarial review** — before design-lock, the drafted design passes an adversarial pass by FRESH independently-dispatched agents when `execution_depth.md` §Admission table's Design challenge row admits it: [`/architecture_brainstorm_redteam`](../../commands/architecture_brainstorm_redteam.md) Mode A `--auto`, or an equivalent independent panel. The redteam owns composition and independence; self-review by the designing context never substitutes. Re-review after folds is a later round (`orchestration` §2 *Later rounds*).
   - **Citations resolve BEFORE dispatch.** Run the project's doc-citation verifier where it ships one, and clear every unresolved symbol/path first (a retraction table naming absent symbols is the sanctioned exception — the tool's docstring says so). A panel spent re-checking citations is a panel not spent on the argument: the mechanical check costs seconds, the panel costs hundreds of thousands of subagent tokens. It is a floor, not a substitute — it proves a symbol exists, never that a claim about it is true.
4. **Abstraction inventory** — inventory existing owner families, strategy/config slots and authored surfaces in the touched domains before any new type is committed, per the brainstorm's Step 3 procedure.
5. **Artifact contracts** — the outputs are the same artifacts the human-in-the-loop flow produces, through the same gates. These are artifact-quality gates, not cognition scaffolding — they bind even when the process is free-form:
   - Design doc per [`common.md §5`](common.md) conventions (folder-per-topic, frontmatter, status taxonomy) plus [`architecture_brainstorm`](../architecture_brainstorm/SKILL.md)'s design-doc structure expectations in its Doc-and-review Step 6 design-doc structure section, including the opening At-a-glance section.
   - Parts and `roadmap.md` exist only when `execution_depth.md`'s Decomposition row admits them; otherwise the design doc's milestones feed one plan file.
   - Parts cover [`architecture_brainstorm`](../architecture_brainstorm/SKILL.md) §*Required evidence and artifact gates*: readiness, consolidation and cohesion litmuses, seam ownership, Trigger, integration touch points, and API + Test Pin. Resolve producer-to-consumer dependencies rather than imposing a fixed cognition sequence; review load-bearing commitments before design-lock.
   - Doc self-review per the `architecture_brainstorm` skill's Doc-and-review Step 7 self-review checklist (placeholder / contradiction / no-orphans / seam-ownership / readiness-gate audits).
   - `roadmap.md` is authored only by [`/update_roadmap`](../../commands/update_roadmap.md), which owns the single-executor rule.
6. **Decision ledger** — every autonomously-resolved decision lands in the topic folder's `decisions.md` `## Decided` when it is resolved, in the entry format of [`flow_and_frontier.md`](flow_and_frontier.md) §8, citing its clause 1 source. Post-hoc auditability substitutes for per-decision pre-approval; an unlogged decision is an unauthorized one.
7. **Hard gate** — no implementation (code, scenes, scaffolds) before design-lock approval. Per [`architecture_brainstorm`](../architecture_brainstorm/SKILL.md) §The Hard Gate. **Self-test: a design session produces decisions, not deliverables.** Count the entries this session banked in `## Decided`, `## Frontier`, and `## Out of scope`. Prose written is not the measure; a session that produced a long doc and no banked decisions did not design.
   - **Prototype carve-out (narrow).** A fork the design classifies as *feel-unknowable-by-discussion* — its answer turns on how something reads or responds at runtime — may exit as a `prototype-pending` Part without counting as an unresolved fork at design-lock, PROVIDED `prototypes/<slug>/QUESTION.md` states both the question and the shape of its answer (the project's prototype procedure owns that file). Bank it in `decisions.md` `## Blocked` naming the prototype as the unblocker. Throwaway code on the never-merged `prototype/<slug>` branch is not implementation of this design, so the gate holds. A generic "we'll figure it out later", or a fork whose answer shape cannot be stated, is refused exactly as before. Provisional surfaces are NOT this carve-out: shipping a CLOSED design deliberately minimal, with full implementation deferred to a Part that may itself be pre-design, is post-design-lock implementation governed by the project's prototype procedure in its provisional mode.
8. **Design-lock** — ONE mandatory human checkpoint, before `/update_roadmap` and before any implementation chaining. Present: (a) design summary, (b) the batched `## Frontier` as a frontier round ([`flow_and_frontier.md §9`](flow_and_frontier.md)) — genuinely preference-dependent → multiple live options; clear winner → recommended solution + approve/feedback, (c) the decision ledger, (d) the per-clause compliance report. **Blast-radius litmus** sets presentation depth: greenfield system / new top-level concept / framework ↔ project boundary / shared owner-family or authored-contract refactor / deletion or replacement of an existing system → offer a full section-level walkthrough; below it → summary + ledger suffice. The gate itself is never skipped, whatever the depth. The answered batch is the approval: reconcile the doc to the answers and proceed, and ask again only when reconciliation adds content that no answer implies, or the answers conflict.

## Failure modes each clause exists for

| Without | What ships |
|---|---|
| 1–2 | The agent invents the user's vision — appetite decided silently; downstream Parts inherit it as if chosen |
| 3 | Plausible self-agreeing designs — the designing context can't see its own blind spots, regardless of model tier |
| 4–5 | A well-thought design badly integrated: parallel abstractions, orphaned claims, hand-edited roadmaps |
| 6, 8 | No audit surface — auto-resolving obvious decisions is the whole point, but without the ledger you can't verify they were obvious |
